# YASK — a Kiro-inspired spec-dev workspace suite

> [!NOTE]
> <sub>This project was developed with agentic LLM assistance. Its planning, specifications, criteria and systems design were directed, in detail, by a human developer.</sub>

**Yet Another Spec-Kit.** Go figures! I wasn't satisfied with the spec kits out there, so I took the best of each and made my own.

The first iteration was based on Kiro's rules and guidelines, complemented by GitHub's spec-kit and other community systems; most of the corpus and methodology in this release comes from my own development practice.

<sub>*[3.1+]*</sub>YASK is now a modular workspace suite as well as a spec-dev kit: folders, conventions, playbooks and tools for a project's lifecycle with humans and agents. It keeps state current so anyone can resume, and can move between specification and development phases more flexibly.

**Differences to Kiro:** the same core methodology <small>`(Requirements → Design → Tasks → Implementation)`</small>, expanded to be more flexible, with logical predicates and tighter specification and documentation practices. The specification format stays compatible with Kiro's own.

<small>Special thanks to [@jasonkneen](https://github.com/jasonkneen) for their Kiro documentation set as a point of reference.</small>

**Reports, suggestions and contributions are welcome. Best of luck with your projects!**



## **Why use YASK?**
- **Specification Development:** EARS criteria are condensed but still human-readable, with parseable predicates, components and traces to the check or symbol that proves them. Gates are part of the format: requirements bind after approval, design cites requirement/axiom ids, and stage specs name the architecture requirement they validate. YASK finds gaps and expands only where needed, including intentional ambiguity across development phases; contradictions are caught while they are still cheap to fix.
- **Modular Steering:** `AGENTS.md` automatically regenerates sections: hard rules, a router and a fact map refresh. You can still edit with your own guidelines. Includes playbooks, templates and examples that are selectively read, with guidelines on how to adapt to project needs and preferences. Add your own steering using the front matter format, and it'll be included in the lifecycle. Change any pre-shipped component you want, your own steering takes priority over the template.
- **Workspace Suite:** `ws` maintains tasks, open items and logs as work happens, sweeps finished work, snapshots uncommitted files and settles stopped merges by rule. It lets agents navigate by maps, pointers and section reads instead of loading whole files, and detects secrets, stale state and drift through automatic checks. `ws start` resumes work state from those files.
- **Flexible Uses:** Not limited to software specs; the same state, routing and checks suit project management and knowledge-management systems, and it stays CI/CD-friendly by keeping foreground commands deterministic and background checks out of CI. It supports concurrent people and agents through id-based state, short locks and merge rules, with a scope suited to small and mid-sized teams. Unattended runs are expected: bounded checks, resumable state and generated views let an agent work without a handoff note or a human watching every step.


## **How to Use**
1. Download the template from releases, and edit the header of `AGENTS.md` (name, goal, people, language). Rewrite that file if you wish, but keep the autogenerated WS labels, and write your own README.md at project root.
2. Set an identity with `WS_USER=NAME`, git `user.name`, or `--you NAME`. State commands fail without it; `ws start` only warns.
3. On Windows run `ws-windows-setup.cmd` once. Run `ws start`; it generates `_steering/.ws/`. Run `ws modules`: `software` (EARS requirements, design, stage gates) is on by default, so `ws modules disable software --apply` if the project builds no software.
4. Use `./ws <command>` or `sh ws <command>` on sh; on Windows use `.\ws <command>` in PowerShell or `ws.cmd <command>` in cmd. Nothing is installed or on `PATH`; `ws` finds this folder from wherever you run it.

Daily: start with `ws start`, then keep state current (`session-state.md`); there is no end step. Tools are optional, and every playbook has manual steps. Details: `_steering/.yask/README.md` and `_steering/.yask/conventions.md`.

### **Porting an existing project**
Drop the release on your existing project's root and ask an agent to survey the layout and map what goes where before moving anything. Use `git mv` for mechanical moves into `_workboard/`, `docs/`, `code/` and `_tools/`; add a module for any kind none covers. Leave old material until `ws archive` retires it. Put your overrides in `_steering/`, not in generated `_steering/.ws/`. Verify with `ws index`, `ws map`, `ws check` and `ws start`. Port a CLAUDE.md into AGENTS.md; fuse both when a project has both.

### Updating
`ws update` mirrors a release into `_steering/.yask/` and applies additive reconciliation to your own files. Settings and methods are in `yask.yaml`; command behavior, the transactional cache and update notes are in `_toolstore/ws/README.md`.
